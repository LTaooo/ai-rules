# GitLab CLI

GitLab 操作统一使用 `glab`，不重复编写 CLI 帮助文档。需要具体参数时，先执行对应命令的 `--help`。

## 使用规则

- GitLab 操作不得改用 `curl`、`Invoke-RestMethod`、浏览器自动化或其他 API 客户端。
- 只有没有对应高级命令时，才使用 `glab api`。
- 从用户提供的 URL 或仓库 remote 确认目标 Host 和项目路径。
- 私有 GitLab 或非当前项目，显式传入 `--repo`；不要依赖当前目录猜测目标。
- 需要认证时，检查目标 Host 的 `glab auth status`；不要索取、打印或复制 Token。
- `glab` 不可用或认证缺失时，直接报告阻塞原因。

## 修改前

- 创建、编辑、关闭、合并、删除、重试或修改变量前，确认 Host、项目、资源 ID 和变更内容。
- 创建 Issue 或合并请求前，先检查已有资源，避免重复。
- 标题或内容缺失时，不创建占位资源，先向用户索取必要信息。
- 外部可见的修改只在用户请求范围内执行。

## 文本处理

- 多行 Issue 或合并请求描述必须使用真实换行。
- PowerShell 中优先使用 Markdown 文件配合 `--description-file`，不要传入字面量 `\n`。
- 示例只使用占位 Host、项目路径和资源 ID，不得包含真实凭证。

## 修改后

1. 记录 `glab` 返回的资源 URL 或 ID。
2. 使用对应的 `glab ... view` 命令回读资源。
3. 检查标题、描述、标签、负责人、状态及其他请求字段。
4. 回复结果 URL 和摘要时，不得暴露认证信息。

如果命令失败，先判断是否可能已经成功，再回读确认；只有修正原因明确时才重试，避免重复创建或重复修改。

## 安全底线

Token、密码、私钥、Cookie 和其他敏感信息不得写入代码、Issue/MR 内容、命令参数、日志、截图或最终回复。
